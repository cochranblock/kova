# Inventory of Source Files

## Rust Files (.rs)

- `android/src/lib.rs`
  - Kova Android entry point. `android_main` (NativeActivity) initializes Android logging, points `HOME` at internal storage so kova's paths resolve, calls `kova::bootstrap()`, then launches the eframe/egui GUI at 2.5 pixels-per-point for high-DPI phones with the `f320` theme. A `MobileApp` wrapper drives the soft keyboard (show/hide based on egui's `wants_keyboard_input`) and delegates rendering to the core `kova::gui::KovaApp`.
- `build.rs`
  - Workspace build script that only prints a loud `cargo:warning` documenting a known future-compat landmine: xml5ever 0.16.2 (pinned transitively via kalosm 0.4.0 → readability 0.2.0) uses a trailing semicolon in macro expression position, which will become a hard error in future Rust. The warning records the fix path: bump readability once kalosm 0.5+ ships.
- `edge/build.rs`
  - Build script for the `edge` crate (ESP32 firmware). Calls `embuild::espidf::sysenv::output()` so the build links against the ESP-IDF toolchain via embuild instead of the regular `esp-idf-sys` flow.
- `edge/src/main.rs`
  - ESP32-WROOM-32 firmware (Phase 1 of the edge plan). Sets up I2C on GPIO 21/22 at 100 kHz, initializes a BME280 sensor, then loops every 2 seconds printing temperature, humidity, and pressure as CSV over serial. Phase 2 (noted in the header) is on-device inference.
- `ios/src/lib.rs`
  - Kova iOS entry point. Exposes `kova_ios_main`, a C-ABI symbol called from Swift/ObjC in the Xcode project (built as a static lib for aarch64-apple-ios). Initializes oslog, sets `HOME` to the app-sandbox Documents dir, calls `kova::bootstrap()`, and runs the eframe/egui app at 2.0 pixels-per-point with the `f320` theme. `run_and_return` must stay false — with it true, eframe returns after the first frame and the caller re-invokes `kova_ios_main`, causing infinite recursion/stack overflow on M1.
- `patches/android-activity/build.rs`
  - Build script for the vendored `android-activity` crate patch. When the `game-activity` feature is on, uses the `cc` crate to compile the C++ sources vendored under `game-activity-csrc/` into three static libs: `libgame_activity.a` (GameActivity + GameActivityEvents), `libgame_text_input.a` (GameTextInput), and `libnative_app_glue.a` (Android's native app glue C file), all linked against `c++_static` plus an explicit `c++abi` link for the static C++ runtime.
- `patches/android-activity/src/config.rs`
  - Defines `ConfigurationRef`, a cheaply-cloneable, thread-safe handle (`Arc<RwLock<Configuration>>`) over the NDK's `Configuration` struct. Lets any thread read the latest device configuration (screen size/dp, density, keyboard, navigation, orientation, SDK version, night mode, etc.) without deep-copying the large struct; `replace()` updates it in place on configuration-change events so pre-existing references see the new values.
- `patches/android-activity/src/error.rs`
  - Error types for the crate. Public `AppError` (main-thread-only violations, Java/JNI errors, input unavailable) is what the API surface exposes; internal `InternalAppError` wraps `jni` crate errors (`JniError`, `JvmError`, Java exceptions) so the backends can use `From<jni::errors::Error>` without leaking the `jni-rs` dependency into the public API. An `InternalAppError -> AppError` conversion strips JNI details at the API boundary.
- `patches/android-activity/src/game_activity/ffi.rs`
  - FFI module root for the GameActivity backend. Bindings are pre-generated (via bindgen) rather than generated at build time; this file conditionally `include!()`s the correct per-architecture bindings — `ffi_arm.rs`, `ffi_aarch64.rs`, `ffi_i686.rs`, or `ffi_x86_64.rs` — selected by `target_arch` (or the `test` feature for host testing). Carries the usual bindgen lint allowances.
- `patches/android-activity/src/game_activity/ffi_aarch64.rs`
  - Pre-generated bindgen FFI bindings for the aarch64 Android target (~7.7k lines, 2350 symbols). Declares the C APIs the GameActivity backend links against: JNI (`JavaVM*`), Android NDK (`AInputEvent`/`AKeyEvent`/`AMotionEvent`, `AInputQueue`, `AHardwareBuffer`, `AConfiguration`, looper), GameActivity C API (`GameActivity`, `GameActivityCallbacks`, motion/key event structs, soft input and window flags), GameTextInput, and the `android_app`/native-app-glue structs, plus the full Bionic libc surface (signal, time, sched, poll) that bindgen pulled in, with layout tests for each struct.
- `patches/android-activity/src/game_activity/ffi_arm.rs`
  - Pre-generated bindgen FFI bindings (rust-bindgen 0.66.1) for the 32-bit ARM target (`__WORDSIZE: 32`, NDK 25.2). Same shape as `ffi_aarch64.rs` — Bionic/NDK constants, JNI, Android NDK input/looper/hardware-buffer APIs, GameActivity and GameTextInput C APIs, and the `android_app` native-glue structs — with 32-bit-specific layout (e.g. `__WORDSIZE`, pointer size) baked in. Selected by `ffi.rs` when `target_arch` is `arm`/`armv7`.
- `patches/android-activity/src/game_activity/ffi_i686.rs`
  - Pre-generated bindgen FFI bindings (rust-bindgen 0.66.1) for the 32-bit x86 target (`__WORDSIZE: 32`, NDK 25.2). Same content as `ffi_aarch64.rs` — Bionic/NDK constants, JNI, NDK input APIs, GameActivity/GameTextInput C APIs, native-app-glue structs — with the 32-bit x86 ABI/layout. Selected by `ffi.rs` for `target_arch = x86` (mainly emulator/debug builds).
- `patches/android-activity/src/game_activity/ffi_x86_64.rs`
  - Pre-generated bindgen FFI bindings (rust-bindgen 0.66.1) for the 64-bit x86_64 target (`__WORDSIZE: 64`, NDK 25.2). Same content as `ffi_aarch64.rs` (Bionic/NDK constants, JNI, NDK input APIs, GameActivity/GameTextInput C APIs, native-app-glue structs) with the 64-bit x86_64 ABI/layout. Selected by `ffi.rs` for `target_arch = x86_64` (mainly emulator/debug builds).
- `patches/android-activity/src/game_activity/input.rs`
  - Safe Rust wrappers over GameActivity's double-buffered C input structs. Defines the `InputEvent` enum (`MotionEvent` / `KeyEvent` / `TextEvent`) plus `MotionEvent` (action, pointers via a `PointersIter` of `PointerImpl`, meta/button state, edge flags, timing) and `KeyEvent` (key code, scan code, repeat count, flags), each thinly wrapping the raw `GameActivityMotionEvent` / `GameActivityKeyEvent` C structs by reference. Modeled on android-ndk-rs's `event.rs`, with `Source`/`Class` enums defined from the Java docs since some sources aren't exposed via the AInputQueue API.
- `patches/android-activity/src/game_activity/mod.rs`
  - The GameActivity backend implementation. `AndroidAppInner` holds the JVM, `android_app` glue pointer, `ConfigurationRef`, `NativeWindow`, key-character maps, and the input receiver; `poll_events()` drains the ALooper + input queue and converts C key/motion events (via lending iterators over the double-buffered `InputBuffer`) into the crate's `PollEvent`s. Also implements soft-input show/hide, text input state bridging (with a C callback `map_input_state_to_text_event_callback`), `StateSaver`/`StateLoader` for the saved-state byte buffer, window flags, asset/data paths, and the C entry points — `android_main`, `GameActivity_onCreate`, `Java_com_google_androidgamesdk_GameActivity_initializeNativeCode`, and `_rust_glue_entry` — that the GameActivity C++ glue calls back into.
- `patches/android-activity/src/input/sdk.rs`
  - JNI bindings + safe wrappers over Android's `KeyCharacterMap`. The `pub(crate)` `KeyCharacterMapBinding` (shared by `Arc`) caches the class and method IDs for `get`, `getDeadChar`, and `getKeyboardType` up front so per-event calls are `call_method_unchecked` fast paths. The public `KeyCharacterMap` maps a keycode + meta-state to `KeyMapChar` (`Unicode` / `CombiningAccent` / `None`, decoding the `0x80000000` dead-key bit) and queries the keyboard type as a `KeyboardType` enum (Numeric/Predictive/Alpha/Full/SpecialFunction plus a `__Unknown` catch-all for SDK extensibility). All JNI failures are funneled through `jni_utils::clear_and_map_exception_to_err` so no `jni-rs` types leak into the public API.
- `patches/android-activity/src/input.rs`
  - Shared input vocabulary used by both backends. Defines `Source` (touchscreen, keyboard, gamepad, mouse, dpad, joystick, trackball, touchpad, etc. backed by a `SourceFlags` bitflag), the `MetaState`/`ButtonState`/`EdgeFlags`/`KeyEventFlags` bitflag structs, and the `MotionAction`, `KeyAction`, `Button`, `Axis`, `ToolType`, and large `Keycode` enums covering the full Android keycode table — all SDK-derived enums use the `__Unknown(u32)` catch-all convention. Also holds the soft-input `TextSpan`/`TextInputState` and the `Pointer`/`PointersIter`/`InputIterator` lending handles that the backend event iterators expose (thin wrappers over each backend's raw event, converting values through the crate's own enums so unknown future SDK variants survive round-trips).
- `patches/android-activity/src/jni_utils.rs`
  - JNI VM/exception utilities. `CloneJavaVM` is a cheaply-cloneable wrapper over `jni::JavaVM` (clone re-wraps the raw VM pointer) marked `Send + Sync` so it can be shared across threads. `clear_and_map_exception_to_err` is the `.map_err()` companion for JNI calls made outside a native method: since there's no Java frame to unwind into, it grabs the pending `JThrowable`, pulls `getMessage()` inside a local frame, clears the exception, and returns `InternalAppError::JniException` (a TODO notes fetching the Java backtrace is unimplemented). `device_key_character_map` looks up `InputDevice.getDevice(id).getKeyCharacterMap()` and wraps the result in a global ref to build a `KeyCharacterMap`.
- `patches/android-activity/src/lib.rs`
  - Crate root. Long module docs frame it as the Rust equivalent of `android_native_app_glue.c`: standalone apps build as `cdylib` with a `#[no_mangle] android_main`, and before `android_main` runs the crate forwards stdio to logcat, registers the `JavaVM`/`Activity` with `ndk_context`, and attaches a Looper to the native thread. `compile_error!` guards enforce that exactly one of the `game-activity`/`native-activity` features is on (with a message explaining double-linked-version failures and pointing at `[patch]`), and `activity_impl` is `#[cfg_attr]`-aliased to the selected backend module. Public API: `MainEvent` (lifecycle, window, focus, config, low-memory, `SaveState`/`Resume` with saver/loader), `PollEvent` (Wake/Timeout/Main), `InputStatus`, `WindowManagerFlags`, `Rect`, and the main handle `AndroidApp` — an `Arc<RwLock>`-based, cheaply-clonable, `Send + Sync` object exposing `poll_events`, native window/config/content-rect access, window flags, motion-axis toggles, soft input + text input state, input-event iteration, per-device key character maps, SDK version, and data/asset paths.
- `patches/android-activity/src/native_activity/glue.rs`
  - The C-facing half of the NativeActivity backend. `WaitableNativeActivityState` is the `android_app` struct handed to C, with mutex/condvar-guarded state shared between the Java-side `ANativeActivity` callbacks and the native thread; `NativeActivityState` holds the msg pipe fds (command channel), config, saved-state, input queue, window, content rect, activity/thread state, and pending window/queue slots. The extern "C" `on_*` callbacks (lifecycle, window created/resized/redraw/destroyed, input queue created/destroyed, config/focus/low-memory/content-rect changes, save-instance-state) update state under the lock and signal the condvar. `pre_exec_cmd`/`post_exec_cmd` serialize/deserialize `AppCmd`s (with `TryFrom<i8>`) across the pipe into the native thread's event stream, and `request_save_state` implements the round-trip save-state handshake. `ANativeActivity_onCreate` is the C entry point that sets up state, forwards stdout/stderr to logcat, spawns the native thread, and invokes the app's `android_main`.
- `patches/android-activity/src/native_activity/input.rs`
  - NativeActivity input event wrappers. `MotionEvent` and `KeyEvent` are lifetime-scoped `#[repr(transparent)]`-style wrappers over `ndk::event::MotionEvent`/`KeyEvent` (with `into_ndk_event` to hand back to the input queue for disposal). They deliberately call `ndk_sys` C functions directly (e.g. `AInputEvent_getSource`, `AMotionEvent_getAction`) rather than ndk-rs methods, so values pass through the crate's own `Source`/`MotionAction`/`Keycode` enums and unknown variants added in newer Android SDKs are captured by the `__Unknown` catch-all instead of being dropped. `MotionEvent` exposes action/pointer metadata plus `pointers()`/`pointer_at_index()` returning the shared `Pointer`/`PointersIter` lending handles.
- `patches/android-activity/src/native_activity/mod.rs`
  - NativeActivity backend implementation (the `activity_impl` module when the `native-activity` feature is on). Constructs `AndroidAppInner` (JVM, `NativeActivityGlue`, ALooper pointer, `KeyCharacterMapBinding` + per-device `KeyCharacterMap` cache, input receiver) and prepares an `ALooper` attached to the cmd-pipe fd. `poll_events()` drains looper events — reading `AppCmd`s off the pipe, translating lifecycle/window/config/input-queue commands into `MainEvent`s, and attaching input queues to the looper — while `input_events_iter()` provides the lending iterator that drains the `AInputQueue`. Also implements `StateSaver`/`StateLoader` (backed by the save-state handshake), `AndroidAppWaker` (a cloneable `NonNull<ALooper>` handle whose `wake()` calls `ALooper_wake`, usable as an async task waker to interrupt a blocked poll), soft-input show/hide and text-input state bridging through the Java activity, and the public `android_main` entry point that spawns the app's `android_main` function.
- `patches/android-activity/src/util.rs`
  - Platform utilities. `try_get_path_from_ptr` converts a C string pointer to a `PathBuf` (None for null/empty/invalid UTF-8), `android_log` maps `log::Level` onto `__android_log_write` priorities, and `forward_stdio_to_logcat` dup2's stdout/stderr onto a `pipe2` pipe and spawns a "stdio-to-logcat" thread that line-reads it and forwards each line to logcat under the tag `RustStdoutStderr`. `log_panic` logs a caught panic payload (String/&str or "UnknownPanic"), and `abort_on_panic` runs a closure under `catch_unwind` and `abort()`s on panic — used at JNI callback boundaries because unwinding past JNI is UB (a TODO notes throwing a Java exception instead of aborting, since an Activity doesn't necessarily own the whole process).
- `src/academy.rs`
  - MoE-powered autonomous development agent ("the do-all module"). `explain_trace` (f115) keeps the old Kalosm-based signature for `serve.rs` compat but now asks the IRONHIVE cluster (`T193::default_hive`) to narrate a pipeline trace (intent, user msg, stage, outcome, retries, stderr, chain) with the project's Cursor rules injected as system context. `f301` is the main pipeline: `gather_context` builds a `T90` project snapshot (file count, line counts, per-file summaries, module list, commands, Cargo.toml), the cluster plans the task into `T182` steps (ReadFiles/GenerateFile/EditFile/RunCommand/GitCommit), each step executes via `moe_generate` (multi-expert) or `single_generate`, `verify_project` runs cargo check and `fix_step` runs a capped fix loop (DDI note: effectiveness drops after 2-3 attempts), and `do_git_commit` commits with a generated message when `auto_commit` is set. Configured by `T185` (project_dir, num_experts, max_fix_retries, num_ctx, auto_commit, dry_run) and returns `T186` (steps, success, files_changed).
- `src/agent_loop.rs`
  - Agentic tool loop (f147/f148, `t106`=AgentAction). `f147` runs one turn: streams LLM inference (f382 picks local/remote/auto), parses tool calls out of the accumulated response (tools::f140), executes each via tools::f141 with dimmed stderr status lines (ok/err + truncated preview), and returns `Done(response)` when no tool calls are found or `Continue { tool_results }` otherwise. `f148` drives turns up to `max_iterations`, auto-compacting the conversation via `context_mgr::f380` under a fixed 8k-token budget (1k system, 512 tools) and trimming each tool output to 1024 tokens (f172) before appending `[tool] ok/err: <preview>` lines to the conversation.
- `src/autopilot.rs`
  - Cursor autopilot (f121): types prompts into Cursor's agent composer with zero API cost. `focus_cursor` finds and activates the Cursor window via `xdotool search --name`, then `run` opens the composer (Cmd+I on macOS, Ctrl+I elsewhere) with `enigo`, sleeps for settle, types the prompt text, and hits Return.
- `src/backlog.rs`
  - Backlog types + loading (f25=load_backlog), formerly in kova-core. `t8` is one backlog.json entry (intent string plus optional project/approuter_dir/cmd/args) and `t9` wraps `items: Vec<t8>`. `f293` maps an entry to the intent enum (`t0`) for full-pipeline, tunnel-update, setup-roguerepo, cloudflare-purge, test, or custom (cmd + args), attaching the project path's file name as a hint; unknown intents return `None`. `f25` reads and serde-parses backlog.json. Includes unit tests for the intent mapping.
- `src/bin/bench-classify.rs`
  - bench-classify: measures the starter classifiers against held-out test sets, anchoring gap 12.2 (no standard-benchmark validation) in real numbers. Loads `starter.nanobyte`, runs the `intent_classifier` over `assets/datasets/kova_intents/test.csv` (33 examples, 10 classes), and prints total accuracy, macro-precision/recall/F1, the 10 lowest-F1 classes with support counts, and the 10 most frequent true→predicted confusion pairs. Adding another (model, dataset) pair is a one-line edit to the `BENCHES` table.
- `src/bin/carve_static.rs`
  - Static corpus carver. Walks `--input-dir` (default `/mnt/data/crates/`), in-memory extracts each `.crate` archive with a GzDecoder, syn-parses every `.rs` file via a `Visit` collector, and emits labeled JSONL per subatomic model to `--output-dir` (default `/mnt/data/training/static/`) — 15 models: async_detector, arg_count (0/1/2/3/4+), return_type, visibility, self_receiver, field_count, variant_count, error_enum, method_count, and the has_debug/clone/serialize/deserialize/default/partial_eq derive detectors. Supports `--max-crates` and progress logging; run behind the `carve` feature.
- `src/bin/kova-test.rs`
  - kova-test: thin binary wrapper (f90=kova_test) that delegates to `kova::f315()` and exits nonzero on error. Equivalent to `kova test`.
- `src/bin/pack-starter.rs`
  - pack-starter: consolidates trained subatomic models into `assets/starter.nanobyte`. Reads `assets/models/{name}/{config.json,weights.bin,bias.bin}` for the five starters (slop_detector, code_vs_english, lang_detector, intent_classifier, t2_coordinator), concatenates `[W | b]` into one f32 blob per model (`num_classes * feature_dim + num_classes` floats), validates that config.json's name matches the directory, and writes the packed file via `nanobyte::Nanobyte` + `PackInput` (manifest carries name/tier/feature_dim/num_classes/class_names so the reader can split the blob back).
- `src/bin/retrain-starters.rs`
  - retrain-starters: re-trains slop_detector / code_vs_english / lang_detector at FEATURE_DIM=8192 (gap analysis 12.1). The original starters used hash dim 256, whose Weinberger-2009 tail bound implies ~98% trigram collision rate — a hard quality cap; 8192 drops that to ~58% at the cost of ~290 KB of starter growth. Delegates to `swarm::train::f395` and writes into `assets/models/`.
- `src/bin/train-intent.rs`
  - train-intent: trains the banking77 intent classifier subatomic model. Reads `assets/datasets/banking77/{categories.json,train.csv}` (validated at 77 classes), trains a trigram-hash → linear classifier at FEATURE_DIM=4096 (~315K params, ~1.25 MB) over 30 epochs, and writes to `assets/models/intent_classifier/`. The 4096 hash dim is a documented compromise between the gap-analysis-flagged 256 (~98% collision floor) and 8192+ (~2.5 MB), landing at ~77% collisions per the Weinberger bound.
- `src/bin/train-kova-intent.rs`
  - train-kova-intent: trains the intent classifier on kova-domain prompts. Reads `assets/datasets/kova_intents/{categories.json,train.csv}`, trains a trigram-hash → linear classifier at FEATURE_DIM=4096 (50 epochs, LR 0.05) over 10 kova intent classes (fix_bug, add_feature, explain_code, refactor, write_tests, write_docs, review_code, run_command, search_code, project_info), and writes weights to `assets/models/intent_classifier/` — replacing the wrong-domain banking77 model that originally shipped as a PoC.
- `src/bin/train-t2.rs`
  - train-t2: trains the T2 "molecular" coordinator on T1 output features. Loads `starter.nanobyte`, runs each kova_intents train.csv example through all 4 T1 models to build 8-float feature vectors (`T2_FEATURE_DIM`), assigns routing labels — code_responder (0) for the six action-oriented intents (fix_bug, add_feature, write_tests, review_code, run_command, search_code) vs prose_responder (1) — trains a linear classifier via SGD (300 epochs), and saves weights.bin + bias.bin + config.json to `assets/models/t2_coordinator/`.
- `src/bridge.rs`
  - bridge (f403=bridge_run): PTY proxy for the Claude Code CLI that logs sessions to `tele/` for retraining. Spawns the CLI in a pty (`portable_pty`) sized to the real terminal via `TIOCGWINSZ`, puts stdin in raw mode (a `RawMode` guard using `cfmakeraw` that restores termios on drop), pumps stdin→pty and pty→stdout bidirectionally, and strips ANSI/VT escapes (CSI, OSC, bare ESC+char) from captured output so the stored training text is clean.
- `src/browser.rs`
  - Kova screen automation — vision-based dual-browser Gemini prompting (feature-gated on `browser`, screen capture macOS-only). Drives two Firefox Gemini windows in an interleaved pipeline: type a prompt into one, switch while it generates, then hover the generated image → click the download button → start a new chat. Pure pixel heuristics, no DOM access: `load_prompts` parses `### label — ...` + "Create a ..." lines from a markdown file; `capture_screen` uses CoreGraphics and converts BGRA→RGBA; `screen_hash` is a cheap stride-997 weighted sum for change detection; `find_generated_image` scans 64px blocks in the middle ~60% of the screen for maximal color variance; `find_download_button` diffs before/after-hover frames near the hover point. Input goes through enigo mouse/keyboard with AppleScript window focus.
- `src/c2.rs`
  - kova c2: T212-tokenized hive orchestration (f18–f23). `T212` is a clap `ValueEnum` over the six intent tokens (f18 build/release, f19 test, f20 full-pipeline, f21 tunnel-update, f22 setup-roguerepo, f23 cloudflare-purge) with `f347` mapping each to its intent constructor and `f349` flagging the three that run locally. `f350` lists the hive nodes (lf, gd, bt, st, mm); `f351`/`f352` do Wake-on-LAN by hardcoded MAC (st/n3 has no WoL); `f353` resolves the project path (arg → `$KOVA_PROJECT` → cwd) and `to_worker_path[_local]` rewrites `~/hive-vault` paths onto the worker's shared/local bases. `f354` (kova_c2_run) builds a plan via `plan::t3::f14` and either runs it locally through `compute::t6` or, for broadcast, requires the project to live under `~/hive-vault` and delegates to `f356` — the one-command sync + build: tar-stream for full sync when a dir is missing, rsync for incremental, then parallel broadcast to reachable non-core nodes from `inspect::f359`.
- `src/cargo/mod.rs`
  - Unified cargo executor — one copy of check/clippy/test shared by pipeline, factory, moe, and academy. `f306` runs cargo with args in a directory returning `(success, stderr)`; `cargo_check` / `cargo_clippy` (`-D warnings`) / `cargo_test` (merges stdout into the output) wrap it. `f307` extracts the core error line (`error[E…]` or first `error` line) as a key for fix-loop detection, `f308` truncates, `f309` extracts the first ```rust (or bare ```) block, `f310` heuristically detects binary-vs-library prompts ("cli", "fn main", "prints"...), and `f311` builds the codegen system prompt (std-only, single rust block, no filler, string-type-matching warnings). Tests cover the extraction/truncation/prompt helpers plus a real cargo check/clippy/test run on a generated temp lib.
- `src/cargo/sandbox.rs`
  - Temp project scaffolding for sandbox compilation (used by pipeline, factory, moe, academy). `f312` writes a minimal `Cargo.toml` (package "gen", edition 2021) plus `src/main.rs` or `src/lib.rs` — lib code gets a `#![allow(dead_code)]` prefix; `f313` is the validation variant that infers binary-vs-lib from the rel_path, and `f314` is a simple always-lib wrapper around `f312`. Includes tests asserting the written layout and prefix behavior.
